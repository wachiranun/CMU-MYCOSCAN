# About the classification model design

This document explains the choices behind `src/mycoscan`. Each choice says what the protocol (sections 2.1 to 2.4) asks for, what the code does, and why.

## The group is the unit, not the image

The CMU study collects 25 to 30 sequence-confirmed isolates per class, 250 to 300 in all. Each isolate has many images: colony obverse and reverse at several growth days, and 10 to 30 microscope fields or Z-planes per slide from two devices. Two images of the same isolate are close to duplicates. If one sits in training and the other in validation, the model can score well by recognising the isolate instead of the species. OpenFungi has the same problem in a different form: it has no isolate identifiers, but many of its photos are repeated shots of one plate.

So the manifest loader derives one `group` column, which is the isolate for CMU rows and a pseudo-group of repeated shots for OpenFungi rows, and everything downstream uses it. `splits.py` assigns whole groups to folds, never single images, and `assert_no_group_leakage` runs before every fold trains. The same rule drives two other places:

- The weighted sampler in `data.py` gives every class the same total weight, and every group within a class the same share. An isolate photographed 30 times does not outweigh one photographed 5 times.
- The bootstrap confidence intervals in `metrics.py` resample groups, not images. Resampling images would treat 30 near-copies as 30 independent cases and make the intervals far too narrow. Groups are resampled within each species, so every replicate contains every class and the macro averages always cover the same classes.
- A CMU row without an `isolate_id`, or an OpenFungi row without a `group_id`, fails at load time. A blank value would otherwise make the image its own group and let it land on the other side of a split from its sibling images. The loader has an explicit opt-out that loads ungrouped OpenFungi rows as one group per image. Only the deliberately leaky `image_random` split uses it (see below).

## Pool A and Pool B: a partition made once

Plan 2 scores its models on OpenFungi images that no model in either plan was trained on (Pool B). That only holds if the partition never changes, so `mycoscan partition` writes it once, to a splits file such as `splits_v1.csv`, and refuses to overwrite it. Every OpenFungi group goes to Pool A (development, 70%) or Pool B (external test, 30%). Within each class, groups are ordered by modality and Pool B takes evenly spaced ones, so every class gives up the same share and the colony and microscopic groups of a class are split in proportion. Pool A groups also get one of 5 folds for grouped cross-validation.

The file records the SHA-256 of the manifest it was built from, and a sidecar (`splits_v1.csv.sha256`) records the file's own hash. A run that names the file in `splits_file` checks both before it starts. It refuses if the manifest has changed since the partition, because a changed manifest can move images between groups. It then merges each group's pool and fold into the manifest, drops Pool B, and with `split = "kfold"` uses the frozen folds. A second defence sits in the data loader: a training loader raises, naming the rows, if any Pool B (or sealed test) image reaches it. That guard catches a wrong config or a future code path that skips the merge.

## OpenFungi pseudo-groups need both signals

`mycoscan build-openfungi` links two images of one modality and class when their perceptual hashes differ in at most 8 bits and their frozen DINO embeddings are closer than 0.15 in cosine distance. Groups are the connected components of those links. Requiring both signals, not either, is deliberate. Connected components are single-linkage clustering, which chains: if A looks like B and B like C, all three become one group. Different plates of one species photographed in one setup can sit within 0.15 of each other in DINO space, so the embedding alone could chain a whole class into one group, and a class with one group cannot be split. pHash alone can link two low-texture plates by accident. The price is that a reshoot changed enough to move its pHash by more than 8 bits stays a separate group. That is why every multi-image group gets a contact sheet, and why both thresholds are config keys to tune after looking at the sheets.

## The CMU test set is sealed by someone else, and only grows

Plan 2's locked test set must be drawn before the modeller sees results, so `mycoscan seal` is a separate command meant to be run by someone else. It takes 15% of each class's isolates, rounded, and writes `split` (`dev`/`test`) and `fold` per isolate to its own hashed file. Isolates arrive in imaging batches over a year, so sealing cannot wait for the last one. It can run once every class has 8 isolates, and a later run only assigns isolates it has not seen: it tops each class's test share back up to 15% and never moves a sealed isolate. A test set that reshuffled whenever a batch arrived would let an isolate the modeller had trained on move into the test set. Within a class, isolates are ordered by batch, year and devices before test picks and folds are spread over that order, so neither the test set nor any fold is one batch or one year.

## The leaky split, kept for comparison

The OpenFungi paper's 99.8% comes from a random image-level split, where near-duplicate shots of one plate sit on both sides. `split = "image_random"` reproduces it: stratified folds of images, ignoring groups, and the group leakage check is skipped. Its `metrics.json` and `config.json` carry `"leaky": true` and its log lines say "leaky, comparison only". It exists only so the pilot report can show the leaky number next to the grouped one.

P0 runs that comparison with `arch = "small_cnn"`, a four-block CNN trained from scratch at 128 px, close in size to the paper's Keras network. It is registered with timm, so it goes through the same registry, adapter, explain layer and linear-probe features as every other backbone, with no special case. The two P0 configs differ only in `split`, and both stay inside Pool A, so the gap between them is leakage and nothing else. The test that demonstrates the gap uses a planted-duplicate set whose labels are unrelated to image content. On realistic synthetic data the grouped split can also score near 1, which would hide the inflation. On the planted set only recognising a seen plate helps, so the grouped split sits at chance and any lift of the leaky split above it is leakage.

## Why k-fold is the headline estimate and 80/20 is kept for the protocol

A single 80/20 isolate split of 25 to 30 isolates per class holds out 5 or 6 isolates per class. That is enough for a go/no-go on overall accuracy but gives per-class estimates with very wide intervals, and in the interim runs on partial data (12 or 20 isolates per class) it leaves some classes with one or two validation isolates. The synthetic set, which has only 2 to 3 isolates per class, shows the extreme case: its holdout fold had no validation isolate for 5 of 10 classes.

The code implements the protocol's 80/20 split (`split = "holdout"`) and records which classes it leaves without validation groups. The default is 5-fold group-level cross-validation (`split = "kfold"`). Every group is validated exactly once, by a model that never saw it, and metrics are computed on the pooled out-of-fold predictions over every development isolate, which is the highest-precision estimate available. Leave-one-group-out (`split = "loio"`) is the most data-efficient option and costs one training run per group. With head-only fine-tuning on a GPU that cost is small.

sklearn's `StratifiedKFold` refuses a fold count larger than every class's member count, which small OpenFungi classes and interim CMU counts can hit. `splits.py` instead deals each class's groups across folds in turn. Each class is spread over as many folds as it has groups, and fold sizes differ by at most one group.

## Staged transfer

OpenFungi has 1,249 images, which is too few to pretrain a CNN from scratch. "Pre-trained weights from OpenFungi" is implemented as a chain:

1. ImageNet weights (or ImageNet-22k, or self-supervised DINO weights) from timm.
2. Fine-tune on OpenFungi (5 genera, colony and microscopic images) with the last block unfrozen (`configs/openfungi_pretrain.toml`).
3. Load that backbone, attach a new 10-class head, and fine-tune on CMU data (`weights = "runs/openfungi_densenet121/model.pt"`).

`finetune = "head"` trains only the new fully connected head, as the protocol says. `finetune = "partial"` also trains the last block and everything after it, such as final norms. `finetune = "full"` trains everything. Frozen BatchNorm layers stay in eval mode during training, so their running statistics keep the pretrained values. LayerNorm has no running statistics, so a frozen LayerNorm only needs its parameters frozen.

Backbones come from timm, so any timm model name is a valid `arch`, and the code reads what it needs from the model itself instead of from a hand-kept registry. The head is the module timm names as the classifier. The blocks are the taps in timm's `feature_info`, and a block runs from just after the previous tap up to and including its own. For ResNet-50 the last block is `layer4`. For DenseNet-121 it is the last transition, `denseblock4` and `norm5`. For ConvNeXt it is the last stage, and for a ViT it is the last transformer block. The explain layer is the last tap. `weights = "imagenet"` takes only weights trained on ImageNet-1k alone. timm's default tag is often a larger pretraining (ImageNet-12k or 21k) fine-tuned on 1k, and taking it would blur the comparison with `imagenet22k`.

The plate crop is decided in one place, `transforms.load_image`, from each image's own modality. Training, evaluation, `Predictor` and `explain` all load images through it, so a `modality = "all"` model crops its colony photos and leaves its microscope fields alone. `densenet121` and `resnet50` were torchvision models before timm, and timm's versions have identical parameter names, so checkpoints from that time still load and predict identically.

`partial_blocks` sets how many blocks `partial` unfreezes. `lora` adds low-rank adapters to every Linear layer outside the head and trains only them and the head. That reaches every attention and MLP layer of a ViT while training a small fraction of its parameters. After training, the adapters are merged into the weights they adapt, so checkpoints stay plain timm models that the web app loads without peft. `layer_decay` (0.8 by default, as the plan sets it) gives each block a learning rate one factor lower than the block after it, and the stem one step lower than the first block. So Stage 2 refines an adapted backbone more gently the closer a layer is to the input. It has no effect on `head`, which trains the head alone. `ema = true` keeps an exponential moving average of the weights, BatchNorm statistics included. Its decay warms up as (1 + n) / (10 + n) towards `ema_decay`, because a fixed 0.999 from the first step would keep most of the untrained weights in a run of a few hundred steps. The averaged model is the one validated and saved, so the reported number is the saved model's.

`linear_probe` is the cheap baseline every backbone gets. Features are extracted once per image with the evaluation transform and cached under a key of everything that changes them, including the manifest's hash, so a changed manifest can never reuse stale features. Only development rows are embedded, since held-out rows are dropped before extraction, and every probe fit passes the same held-out guard as a training loader. The logistic regression is folded into a linear head on the frozen backbone, so a probe run leaves an ordinary checkpoint.

Head-only was the safer default when the study was expected to have only a few isolates per class. With 25 to 30 isolates per class, partial and full fine-tuning become realistic, and which depth wins is an empirical question that the pilot on OpenFungi and the k-fold estimate on CMU data settle.

## One model per modality

Colony photographs and microscope fields share almost nothing visually. The scale, background, colour cues and diagnostic structures all differ. A single model would also be dominated by the microscopic set, which has about 10 times more images. So each config trains one modality (`modality = "colony"` or `"microscopic"`). The checkpoint records its modality so the web app can route an image to the right model. `modality = "all"` still exists for experiments.

Because predictions are stored per image with their `group`, combining the two models for one isolate is a mean over both prediction tables (`metrics.aggregate_by_group`). This matches how a mycologist combines the colony and the slide.

## Preprocessing and augmentation

Every image is first converted to 8-bit RGB. 16-bit microscope frames are min-max scaled, and transparent pixels are placed on white. Training, validation, `Predictor` and `explain` all use the same conversion, `transforms.to_rgb`.

Colony photographs can then be cropped to the Petri plate (`plate_crop = true`), before any other step and for training, validation, `Predictor` and `explain` alike. The plate is the largest region on the other side of an Otsu threshold from the image border, with the colony filled in. The crop is the plate's bounding square, and everything outside the plate circle is set to black. This removes the bench, labels and plate edges that a model could otherwise learn instead of the colony. A photo with no plate-sized region is left as it is. Crops are always regenerated from the raw image by code, so derived images never diverge from the source.

Both training and validation images then get autocontrast, a resize, and ImageNet normalisation. Autocontrast reduces the brightness and contrast differences between microscope cameras and smartphones (protocol 2.1). It applies one luminance stretch to all three channels (`preserve_tone=True`). A per-channel stretch would turn a red pigment patch grey or black.

Only training images are augmented, and `augmentation` picks the recipe. `standard` (the default) uses random crops, flips, right-angle rotations, brightness, contrast and saturation jitter, and occasional blur that mimics an out-of-focus Z-plane. `trivial_wide` uses random crops, flips and TrivialAugment-Wide, which applies one random operation per image at a random strength. `none` gives training images the validation transform. Validation and test images are real images, centre-cropped. Hue is never changed, because pigment colour is diagnostic. The red diffusible pigment of *Talaromyces marneffei* on the colony reverse is one example. TrivialAugment-Wide's Solarize, Posterize, Equalize and AutoContrast operations are dropped because each one changes hue. Equalize and AutoContrast stretch each channel separately. Brightness, saturation and contrast keep hue because they blend towards black or grey. A test checks every recipe against pure pigment patches.

Class imbalance is handled by the group-aware weighted sampler (`imbalance = "sampler"`, the default) or by a class-weighted loss (`loss = "weighted_ce"` with `imbalance = "none"`). The code never applies both, because that would correct the imbalance twice: the config refuses that combination. `loss = "focal"` (with `focal_gamma`) down-weights images the model already gets right, and `label_smoothing` applies to every loss.

## Metrics

For each class (one versus rest) and as a macro average over classes present in the validation data: sensitivity, specificity, PPV, NPV, F1, accuracy and AUC-ROC. A class that is present but never predicted gets PPV 0. Leaving it undefined would drop it from the macro PPV and inflate the average. Overall accuracy is also reported. Everything is computed twice:

- **Isolate level** (primary): the class probabilities of an isolate's images pooled into one prediction, by their mean unless the config says otherwise (see Bags and pooling). This is the clinically meaningful number, since a laboratory identifies an isolate, not a photograph.
- **Image level** (secondary): each image is scored on its own. It is kept for comparison with published image-level numbers, and each block in `metrics.json` carries its `role`.

Each level also gets Top-2 accuracy, since the pre-registered endpoints include a Top-2 threshold, and Cohen's kappa against the reference. Accuracy and Top-2 accuracy get Wilson 95% intervals. These treat a level's units as independent, which holds for isolates but not for the correlated images of one isolate. The isolate bootstrap covers every overall, macro and per-class metric, with 2,000 resamples by default. A class without support gets no interval, and the block says why instead of reporting an empty or degenerate range.

Genus and order accuracy map both the reference and the top-1 prediction to the parent taxon, so calling *F. solani* complex for *F. oxysporum* complex is wrong at species level and right at genus level. The species-to-genus map is read from the whole manifest, not from the prediction table, because one validation fold need not contain every class the model can predict. Subgroup analyses (by device, phase and so on) rerun the same report on each subset, pooling the subset's images exactly as the headline pools them (through their bags first, when there are bags), so a subgroup number means exactly what the headline number means.

An external set labelled more coarsely than the model, such as OpenFungi Pool B (Flavi, Nigri, Fusarium, Rhizopus), is scored through a label map. The model's probabilities are summed into each reference label, not just its top-1 call, so AUC remains defined. Model classes outside the map share one `unmapped` column, so predicting one of them counts as an error and is never quietly dropped.

Every level also reports its calibration: the expected calibration error over equal-width confidence bins and the reliability table behind it. The reject option is an accuracy-coverage curve: the model makes a call when its top probability is at least tau, and says "no call" otherwise. tau is chosen once, by a rule in the config, on the out-of-fold isolate predictions of the development set, and stored in the deployable checkpoint. Evaluating the sealed test set applies that stored tau as it is. Choosing tau on the test rows would make the reported coverage and accuracy at tau optimistic, in the same way that choosing an epoch on validation does, so the function that chooses tau refuses any table with test or Pool B rows. The numbers at tau in a training run's own `metrics.json` are on the rows tau was chosen on, and are optimistic for that reason. tau is a threshold on isolate confidence, so it is reported at the isolate level only. An image's confidence is a different quantity, and applying the isolate threshold to it would describe a reject rule nobody uses.

Training runs a fixed number of epochs and does not pick the best epoch on validation. The validation fold is also the fold the reported score comes from, so picking an epoch on it would make that score optimistic, and with few validation isolates per class in interim runs the optimism would be large.

## Seeds, sweeps and generated tables

The plans report a backbone or recipe as mean ± SD over folds × seeds. Folds come from `seed` alone and each entry of `seeds` only changes initialisation and sampling. So a difference between seeds is training noise, never a different split, and two runs with the same `seed` validate the same groups in the same folds. Every fold of every seed writes its own `metrics.json`, and `mycoscan results` turns a directory of them into the benchmark table, so no number in a report is typed by hand. Cell statistics use the fold rows and leave the pooled rows out, because pooled predictions repeat the folds.

A sweep is a base config plus override cells, each run under a name built from its overrides, so the directory listing documents the sweep. A cell that fails is recorded and the others still run, since one bad cell should not cost a night of GPU time. `train_fraction` removes whole groups per class before any fold is made, so a learning curve never splits a group. With a splits file the folds already exist, so it removes groups per class within each fold, which keeps every class in every fold. With few groups per class this also shrinks the validation folds, so the low-fraction points of a curve are noisier. Every fold records its wall time, device, GPU-minutes and peak GPU memory, so P4 can put cost next to macro-F1.

## Bags and pooling

The plans test how image predictions become an isolate prediction: mean or max over the images of an isolate, over its images per device and then across devices, or over the tiles of one high-resolution image in the pilot, where real field-of-view bags do not exist yet. A bag is built from something inside one group (the isolate, the isolate and device, or the image), so a bag can never mix groups or straddle a fold, and the leakage check runs on bags as well as on groups. Mean and max have no parameters, so training stays single-instance and pooling is applied wherever the model predicts: validation, `mycoscan eval`, and through the checkpoint's stored `bag` and `pooling` the web app. That keeps the image-level and isolate-level numbers about the same model. Mean pooling over an isolate's images is the vote the pipeline always used, so `bag = "isolate"` with `mean` reproduces the earlier isolate metrics. Max pooling takes each class's highest probability over the instances and renormalises, so a single clear field can carry an isolate. Bag batches are padded tensors with a mask, so isolates with 10 and 30 fields share a batch and padding contributes nothing to a pooled value. The prediction table gains a row per bag, told apart by a `level` column, so there is still one output format.

Attention-MIL has parameters, so with it the bag is the training unit: the bag-level loss trains the backbone, the gated attention and a new head together, and an isolate is called from all its fields at once rather than from a vote. Its value to the review is the weights themselves, so every instance's weight is written beside the predictions and each run reports the mean entropy of its bags' weights: a low entropy says the model leans on a few fields, which the concordance review can then check against what a mycologist would look at. The scores of padded instances are set to minus a billion before the softmax and the weights then multiplied by the mask, so padding gets exactly zero weight, not merely a small one. The device-then-isolate hierarchy pools embeddings within a device but weighs device *predictions* across devices, so an isolate's probabilities are exactly the attention-weighted mean of its device rows. That makes the per-device predictions (M5) and the isolate prediction two readings of one model that can be checked against each other from the tables alone, and the bag-level loss is the log of that mixture. Image rows of an attention run score each image as a bag of one, so the image level is still about the same model.

## Late fusion

Plan 2 asks whether a colony branch and a microscopy branch together beat either alone (M4). Each branch is trained and validated on its own, and the fusion works on what the runs already wrote: their out-of-fold isolate predictions, joined on the isolate. A scalar colony weight is the smallest thing that can be fitted, and it is fitted on isolate macro-F1, the primary endpoint. Two runs are fused only when they are genuinely about the same isolates: same classes, seeds and folds, the same test isolates, and every isolate in the same fold in both, since otherwise a fused row would mix a prediction made with an isolate in training with one made without it. The weight is cross-fitted, each fold fused with a weight chosen on the other folds, so the fused out-of-fold score is not flattered by a weight chosen on the rows it scores. A holdout run has one fold and nothing to cross-fit against, so its weight is fitted on that fold and the run says so (`cross_fitted` false). The final weight, chosen on every development isolate, is applied once to the test isolates; test rows never reach a fit, the same rule as tau. The MLP arm uses each branch's frozen initial backbone rather than its fine-tuned networks, because a fine-tuned network has seen the training folds' isolates and would hand the MLP embeddings that separate them better than they separate unseen isolates. The fused run writes the files of an ordinary run, with fold membership hashes combined from the two branches, so the results table and the paired comparison need no special case.

## Sequential against direct: the pre-registered verdict

The primary analysis of Plan 2 compares sequential transfer (ImageNet, then OpenFungi, then CMU) with direct transfer (ImageNet, then CMU) for the same backbone. `mycoscan paired` pairs the two runs fold by fold and seed by seed, so the comparison removes the variation between folds instead of counting it as noise. It reports the mean difference in isolate macro-F1, a bootstrap CI over the pairs and a Wilcoxon signed-rank p, and it states the verdict fixed in advance: sequential is superior only if the CI excludes 0 and the gain is at least 2 points. A gain smaller than that is not worth the extra stage even when it is real. The thresholds are config values written into the output, so the verdict can be checked against the pre-registration. Paired statistics are only valid on genuinely paired runs, so the command refuses runs with different seeds, different test isolates, or different validation images in any fold, and names the first fold that differs. A sequential run that loses is named negative transfer, with the recommendation to use direct transfer, which makes the Stage-1 guard-rail a reported number instead of a judgement.

## Stage-1 checkpoints

`mycoscan export-stage1` trains the chosen backbone and recipe on every Pool A image of one modality and saves it without its head, because the CMU class set is different and a Stage-2 run attaches its own. Pool B is held out by the splits file, and the export refuses to run without one, since it could not otherwise know which images to hold out. The file name carries the modality and the arch (`of_micro_convnext_tiny.pt`), and the checkpoint carries its provenance: commit, manifest and splits hashes, resolved config, and the groups it trained on. A Stage-2 run that names it as `weights` checks the arch, records that only head parameters were newly initialised, and copies the Stage-1 provenance into its own, so a CMU number can be traced back through both stages.

## The web app's entry point and the model card

The web app takes one isolate's images, not one image, so `Predictor.predict_bag` pools them exactly as the model was trained and evaluated to: learned attention for an attention-MIL model, the stored `pooling` for any other, and a tile checkpoint's images cut into their tiles. It reads all of that from the checkpoint, so the web app needs no knowledge of the run's config and cannot pool a model differently from how it was scored. A no-call is the reject option of the calibration work: the top pooled probability below the checkpoint's tau, which was chosen on development isolates. The Top-2 is returned with a no-call too, because a mycologist referring the isolate still benefits from the two likeliest classes. `predict` stays as it was, so existing callers keep working.

`model_card.json` sits beside every deployable `model.pt` so whoever deploys a model reads, in one file, what it is for, which classes and modality it calls, its tau, which data it was trained on (by hash, so it can be checked against the manifests) and how it scored. The headline metrics are those of the predictions the run actually scored: the validation set for a holdout run, and for a cross-validated run the out-of-fold development predictions of the seed the final model was trained with, which estimate a model trained on all isolates. The sealed test set never appears, because training never sees it; its numbers come from `mycoscan eval`.

## Provenance

A number in the pilot or main-study report is only worth quoting if it can be traced to the exact code, data and settings that produced it. So every training and evaluation run writes a `provenance` block into `metrics.json`. The block holds the git commit and a dirty flag, the SHA-256 of the manifest (and of the splits file or checkpoint), the resolved config, and package versions. The git state is read when the run starts, so editing code during a long run does not change what is recorded. Untracked files count as dirty, because a new module can change what runs. `data/` and `runs/` are git-ignored, so they never do. MLflow logging is optional (`tracking = "mlflow"`), because the suite and the Colab, Kaggle and cluster environments must work without a tracking server. The file is always the record, and MLflow is a convenience view of it.

## Explainability

`explain.py` computes a class-attention map and SmoothGrad saliency, which is the mean absolute input gradient over 25 noisy copies. The map is picked from the checkpoint. For a CNN it is Grad-CAM on the backbone's last feature tap (`features.norm5` for DenseNet-121, `layer4` for ResNet-50). Gradients flow from the input image, so Grad-CAM also works when the backbone is frozen. A ViT's last tap outputs tokens, not a feature map, so for a ViT it is attention rollout: each layer's attention averaged over heads, with the residual connection added, multiplied through the layers and read from the class token to the patches. timm's fused attention never materialises the attention matrix, so rollout switches it off for its one forward pass and restores it afterwards.

Each image gets a three-panel PNG (original, map overlay, saliency) and a row in `review_sheet.csv`. That sheet is the record for the protocol's concordance review (2.4). Two raters judge independently whether the map points at the diagnostic structure (conidiophores, hyphae, spores, colony texture), partly at it, or at background and artifacts such as plate edges, labels, scale bars and dust. A 3-point scale is coarse on purpose: it is what two raters can apply consistently. Agreement is reported as Cohen's kappa, from the same code that scores the model against the reference. The review is blinded: the panels and the sheet show the model's call but not the true label, and not the image path, because OpenFungi paths name the class. `review_key.csv` holds the mapping back. Images are drawn at random per class, with a seed, from a named pool, normally the test pool, so the review sample is reproducible and not hand-picked.

An attention-MIL model calls an isolate from all its fields at once, so a per-image map would explain a prediction the model never makes. It gets one panel per bag instead: the fields ordered by attention weight, each with its weight, and the map of the top three fields for the bag's call. The weights say which fields drove the call, and the maps say where in those fields the model looked; the rater's question is unchanged, so the bag rows carry the same rater columns and are scored by the same code, told apart by `level`. With a device-then-isolate hierarchy the weight shown is the field's share of the isolate (its weight in its device times the device's weight), since the weights within a device alone do not compare across devices. Bags are drawn whole per class, so a panel is never a partial isolate. Mean and max pooling have no learned weights (mean weighs every field 1/n), so a bag panel would show nothing the per-image panels do not; such checkpoints get image panels and the log says why.
